## Manual NFSv4 mapping

Passed through the UI against the actual NAS: Add location → NFS export → enter its tailnet IP and `/tank/data/NAS` → select NFSv4 → Connect. Verified `NFS · Connected` and the real export listing including `Logs`.

Environment correction: Ubuntu's installed libnfs was 5.0.2, below the documented 6+ requirement. Built the repository-pinned libnfs commit `c69a48c8116fd50287875decd50474685937a4af` in the isolated test directory and set `LIBNFS_LIBRARY` explicitly. The unprivileged connection then returned `NFS4ERR_PERM`; the same diagnostic connection with privileges succeeded. The UI pass used a separate privileged instance (8767, SSH-forwarded to 8100), matching the documented system-service privilege model. No NAS export permissions were changed. This is an Ubuntu service connecting to its own NFS export, with the browser on the Mac; it does not prove a Mac-hosted NFS connection.

## Cross-platform protocol operations and discovered fixes

Completed the same Playwright operation sequence against the actual Mac, Windows VM and Ubuntu services, for **both SMB and NFSv4** connections to SmartNAS. Each run manually entered the host/share or export, verified the real root listing, entered a dedicated disposable NAS folder, created a child folder, persisted/reopened a favourite across page reload, created/saved/reopened a text file, deleted that file, removed the favourite, and recursively deleted the child folder containing its nested directory. All six protocol runs passed. The browser ran on the Mac; the filesystem and protocol workers ran on each named service host. This does not claim native Windows-browser coverage.

The Windows local-filesystem sequence also passed. Evidence is in `windows-operations.json`, and `<host>-<smb|nfs>-operations.json` plus matching screenshots in the local evidence directory. Protocol runs deliberately do not record traces containing real SMB credentials. Credentials came directly from BWS and were not committed or printed.

NFS write checks used `remotefs-protocol-dogfood-20260911` under the NAS export. The export's squashed UID/GID cannot write at its root (owned by root:users), so a dedicated directory owned by the test identity was created without changing export permissions or existing data. Mac and Windows protocol passes did not require additional host privilege changes; Ubuntu used the separate system-service test instance described above.

Two actual product bugs were found and fixed:

1. **Installed CLI SMB import collision:** Impacket's adjacent `smbclient.py` console script shadowed smbprotocol's package when launching `remotefs`. The CLI now excludes its launcher directory from the import path. A subprocess regression covers both launcher names and spawned workers. The installed standard launcher then passed manual SMB mapping on SmartNAS.
2. **SMB replacement/conflict handling on non-executable files:** smbprotocol's rename helper requests execute access on an existing destination while resolving its path. SmartNAS rejected normal 0664 text files. The adapted rename transaction uses metadata access instead, retains atomic replacement/no-overwrite semantics, and checks resolved share identity. The upstream MIT notice is included in source/wheel distributions. The Samba fixture now creates non-executable files; real SMB and NFS integration checks pass write/read/archive/conflict/replace/copy/folder-move/delete.

After these fixes: **126 Python tests passed, 1 skipped; 8 frontend tests passed** (frontend unchanged since that run). Updated wheel built and its adapted-code licence inclusion was checked. Mac uses the current checkout; updated wheels were installed in the Windows and Ubuntu test environments.
